Ordinal 분류 헤드 — CORN 미완 < 완료 < 과조리 순서를 보존하는 순위일관 분류

3단계 + 신뢰도 + 중심온도 ──▶ MQTT · cooking/status ──▶ Pi 5 대시보드
왜 late fusion인가? 두 카메라와 열배열은 서로 다른 물리량을 보고 픽셀 정합이 안 된다. early(채널 스택) 융합의 이점은 정합이 전제라 우리 구성엔 안 맞음 → 브랜치별로 뽑아 뒤에서 합치는 late가 안전한 기본값. (온도만 gated attention으로 예외 처리)
02

물리 배치 · 네트워크

기기가 셋(Jetson·Pi·로봇)이고 Jetson의 랜포트는 1개뿐 → 직결 대신 기가비트 스위치로 묶는다. 셋 다 MQTT로 대화하고, 무거운 솥 영상만 별도 경로로 뺀다.

경로 ① · MQTT

열화상 32×24

영상 아님 — 768개 숫자배열을 MQTT로 보내 대시보드 JS가 히트맵으로 렌더. 가볍고 우아.

경로 ② · MJPEG HTTP

솥 RGB 영상

조리는 느려 저(低)fps로 충분. Jetson의 작은 HTTP 서버 → 대시보드 <img>. RTSP/WebRTC는 오버킬.

왜 케이블이 3개(Jetson은 1개)? Jetson 랜포트가 1개라 Pi·로봇 2개를 직접 못 뽑는다 → Jetson은 스위치로 1개만, 스위치가 Pi·로봇으로 분배.  ·  ⏱ 시간동기 주의: 타임스탬프 정합이 중요한데 스위치만 쓰면 인터넷이 없어 NTP 불가 → 공유기(인터넷)로 NTP를 쓰거나 로컬 시간서버를 둔다.
03

무엇을 보고 판단하나 — 색이 아닌 신호

튀김과 달리 국/탕은 표면 색 변화가 약하다. 그래서 색 대신, 문헌이 "색 없이도 학습된다"고 검증한 세 가지 시각 신호 + 온도를 쓴다.

04

정답(GT)과 라벨링 파이프라인

"완료"의 정답을 사람이 일일이 찍지 않는다. 온도·시간 약지도 스크립트가 본체로 대량 자동 라벨을 만들고, 사람은 검수와 경계만 손본다.

A

동기 수집 자동

RGB 2뷰 + 열배열 + 중심온도를 공통 타임스탬프로 저장. 조리 시작~과조리까지 촬영(안 그러면 과조리 라벨이 안 생김).

B

약지도 자동 라벨 자동 · 스크립트

중심온도+시간+색을 클러스터링(도미 논문 방식) → 프레임에 미완/완료/과조리 자동 부착. 라벨의 대부분을 여기서 생성.

C

완료↔과조리 경계 앵커 수작업 · 소량 필수

둘 다 끓는점 이후라 온도만으로 못 가른다. 이 경계만 사람이 소량 직접 라벨해 클러스터를 보정.

D

GUI 검수 조연

whole-frame 분류라 무거운 툴 불필요. Label Studio 또는 CVAT(무료, 편한 쪽)로 검수. 거품 bbox를 넣을 때만 Roboflow. → CVAT는 기본값이지 유일 정답 아님.

소량 데이터 대비책 — 전이학습(MobileNet, 1 epoch로 급수렴) + 자기지도 보조손실(오차 4~27%↓) + 온도·시간 약지도. 과제라 데이터가 적은 걸 이 세 겹으로 메운다.
