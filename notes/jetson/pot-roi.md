# jetson/pot-roi — top view 솥 ROI 자동 검출 (2026-10-10)

사용자 요청: 카메라는 솥만 보도록 ROI를 적용하고 싶다. 솥 검출 모델 학습은 하지 않는다.

## 결정 제안 (D 번호는 병합 담당이 부여)
- **결정:** 원본 프레임은 전체 화면 그대로 저장하고, 솥 ROI는 **세션 중 주기적으로 원을 검출**해 기록한다. 분석 때 그 원을 마스크로 쓴다.
  검출은 고전 영상처리(허프 원 + 테두리 일치 점수)로 하고 학습 모델은 쓰지 않는다.
- **이유:**
  - 카메라와 인덕션은 고정이지만 **솥은 회차마다, 조리 중에도 밀린다.** 실측 중심 x값:
    10/07 세션 1060~1067·1006~1010, 10/10 세션은 10분 동안 1067→1100, 10/10 저녁 1020~1024.
    그래서 고정 상수 ROI는 맞지 않는다.
  - 녹화할 때 잘라 버리면 ROI가 틀렸을 때 되돌릴 수 없다.
  - 정답이 원 하나뿐인 문제다. 고전 방법으로 실물에서 충분히 맞으니 라벨링·학습·검증 비용을 들일 이유가 없다.
- **대안:**
  - 고정 ROI 상수: 솥이 밀려서 기각.
  - 녹화 시점에 잘라서 저장: 되돌릴 수 없어서 기각.
  - 솥 검출 모델 학습: 비용 대비 이득이 없어서 기각.

## 구현
- `app/roi.py`
  - `detect_pot(image)`: 긴 변 640 px로 축소 → medianBlur 7 → HoughCircles(반지름은 긴 변의 14~22%로 제한) →
    후보 8개의 테두리 일치 점수를 비교해 가장 높은 후보를 고른다.
  - **테두리 일치 점수:** 원 둘레 360점 중 Canny 에지(3×3 팽창) 위에 놓인 비율이다. 0.65 미만이면 못 찾음으로 처리한다.
  - **반지름 통일:** 솥은 안쪽 벽 윗선(r≈322)과 바깥 테두리(r≈351)가 동심원 두 개로 잡히고, 허프는 회차마다 둘 중 하나를 고른다.
    그래서 같은 중심에서 반지름을 훑어 기준을 넘는 **가장 큰 원(바깥 테두리)**으로 통일한다. 이 처리를 넣은 뒤 반지름이 351~354로 안정됐다.
  - `PotRoiTracker`: 수집 루프는 `offer`만 부른다. 변환·검출은 전용 스레드 하나가 하고 대기열은 1칸이다.
    검출 중에 들어온 프레임은 넘기므로 수집을 막지 않는다. 첫 검출은 3초 뒤, 이후 60초마다 한다.
  - **사건 기록:** 첫 검출은 `pot_roi.found`로 남긴다. 직전 검출보다 중심이 긴 변의 3%(1920 기준 58 px) 넘게 움직이면 `pot_roi.moved`(warn)로 남긴다.
- `session.py`
  - 미리보기의 이미지 변환을 `_sample_bgr`로 분리했다. 미리보기와 ROI 검출이 같은 변환을 쓴다.
  - 녹화 세션: 검출 결과를 `<session>/pot_roi.jsonl`에 한 번에 한 줄씩 남긴다. 종료 시 session.json `pot_roi.summary`에 센서별
    `tried`·`found`·중앙값 `circle`·`max_shift_px`를 쓰고, manifest에 `pot_roi.jsonl`(role `derived`)을 넣는다.
  - 라이브 세션(`record:false`): 결과를 메모리에만 둔다.
- API
  - `GET /api/v1/capture/pot_roi`: 최신 검출 결과.
  - `POST /api/v1/capture/pot_roi/redetect`: 바로 다시 찾기.
  - 둘 다 `docs/pi-jetson-api.md`에 정리했다.
- viewer: 미리보기 위에 초록 원과 중심점을 겹쳐 그리고, 점수·성공 횟수·마지막 실패 사유와 **"솥 다시 찾기"** 버튼을 보여 준다.
- 설정
  - `COLLECTOR_POT_ROI_SENSORS`(기본 `cam_rgb_0`, `off`로 끔), `_FIRST_DELAY`(3), `_INTERVAL`(60), `_MIN_SCORE`(0.65).
- `tools/pot_roi.py`
  - `image`: 사진 한 장을 검출한다.
  - `session`: 저장된 세션을 N초 간격으로 다시 계산한다. `--out`으로 JSON, `--overlay`로 확인용 그림을 남긴다. 원본에는 쓰지 않는다.

## 검증
- **오프라인 실측(저장 세션 3개, 60초 간격):**
  - `check-20261010T082718Z`: 10회 중 9회 찾음.
  - `check-20261007T112328Z`: 10회 중 6회 찾음. 앞쪽 4회는 솥 없이 상자를 올려 둔 장면이라 맞게 거부했다(점수 ≤0.57).
  - `check-20261007T114230Z`: 4회 중 3회 찾음.
  - 반지름은 351~354로 안정적이다. 겹쳐 그린 원이 바깥 테두리와 맞는 것을 눈으로 확인했다.
- **점수 분포:** 솥이 있는 프레임 0.65~0.94, 솥이 없거나 가려진 프레임 0.36~0.64. 기준 0.65는 경계에 가깝다.
  한 번 놓쳐도 1분 뒤 다시 찾고, 요약은 중앙값을 쓴다.
- **실물 라이브 확인(10/10 20:51 KST):** worktree 코드를 127.0.0.1:8020에 운영 env로 띄우고 `cam_rgb_0` 라이브 세션을 열었다.
  UYVY 프레임에서 검출이 됐다(중심 1024,772, r 351, 프레임 수신 후 146 ms).
  redetect를 7번 실행해 6번 찾았다. 놓친 1번은 오른쪽 테두리를 가리는 브래킷 때문으로 보인다.
  data_root에 새 항목은 생기지 않았고, 운영 8000은 손대지 않았다.
- 검출 1회는 약 108 ms(1920×1536, Jetson CPU)이고 1분에 1번이다.
- 테스트 6개 추가(`tests/test_pot_roi.py`): 합성 솥(바깥 테두리 선택), 솥 없음 거부, 요약, 녹화 세션 jsonl·session.json·manifest·사건,
  라이브 무저장, 끔·세션 없음 404. 전체 **75 통과**.

## 인계 / 남은 일
- **Fedora(`research/soupdata/camera.py`):** 기본 `ROI=(0.25,0.25,0.75,0.75)` 사각형 대신 session.json `pot_roi.summary.cam_rgb_0.circle`을 쓰는 게 좋다.
  - 쓸 수 있는 값은 `cx`·`cy`·`r`, 또는 `norm`, `bbox_ratio`다.
  - 원형 마스크를 권장한다. 국물만 보려면 r×0.9(안쪽 벽 ≈ 322/351)로 줄인다.
  - 조리 중 솥이 움직이면 `pot_roi.jsonl`의 시각별 원을 쓴다.
  - 기능이 생기기 전 세션은 `tools/pot_roi.py session`으로 다시 계산한다.
- 김 서림·뚜껑·손·국자로 테두리가 가려지면 못 찾음이 늘 수 있다. 조리 세션의 `found/tried`를 보고 기준값을 다시 정한다.
- 열화상 ROI는 같은 방식으로 따로 한다(데운 솥이 열화상에서 원으로 보일 때 측정). top view와 정합하는 작업과 함께 진행한다.
- 운영 반영: main 병합 후 사용자가 `jetson-collector`를 재시작해야 한다(세션이 없을 때).
