# 의사결정 기록 (Decision Log)

> 기술 선택·설계 결정을 남긴다. 형식: **결정 / 이유 / 대안 / 날짜**

## D-001 · 대시보드 우선 개발

- **대안:** AI 추론부터 개발 — 그러나 출력 스펙이 안 잡혀 대시보드와 계속 어긋날 위험.
- **날짜:** 2026-07-10

## D-002 · 대시보드 스택 = React + Vite
- **결정:** React + Vite로 웹 대시보드 구축.

- **대안:** Streamlit/Dash(빠르지만 커스터마이징 제한), Next.js(Pi에 과함).
- **날짜:** 2026-07-10

## D-003 · 통신 방식 = MQTT
- **결정:** Jetson ↔ Pi 통신은 MQTT. Pi에 Mosquitto 브로커, 브라우저는 MQTT-over-WebSocket으로 직접 구독.
- **이유:** 실시간 텔레메트리에 표준적으로 최적. pub-sub이라 로거/알람/액추에이터 추가가 쉬움(느슨한 결합). 별도 백엔드 서버 불필요.
- **대안:** WebSocket 직결(양방향 간단하나 다중 구독/확장 약함), REST 폴링(단순하나 실시간성 낮음).
- **날짜:** 2026-07-10

## D-005 · Jetson에서도 git 커밋/푸시 허용
- **결정:** Jetson 실기기에서 생성한 산출물(벤치 결과, 노트)은 Jetson에서 직접 커밋·푸시한다.
  단 작업 전 `git pull`을 먼저 해 히스토리 분기를 막는다. 무인(headless) 에이전트의
  main 커밋·push 금지 규칙은 그대로 유지(사람이 대화형으로 작업할 때만 해당).
- **이유:** 기존 "Jetson은 읽기 전용" 규칙은 히스토리 분기 방지 + 무인 규칙과의 일관성이 목적이었으나,
  실측 데이터를 dev 머신으로 수동 이동 후 커밋하는 것이 더 번거롭고 누락 위험이 큼.
- **대안:** 결과 파일 scp/USB 이동 후 dev 머신에서 커밋(수작업·누락 위험), Jetson 전용 브랜치(과함).
- **날짜:** 2026-07-13

## D-006 · 원시 데이터 저장 = Jetson 로컬(핫) + (옵션) 원격 아카이브(콜드)
- **결정:** 학습용 원시 데이터(RGB 이미지 2대·열화상·중심온도)는 **Jetson 로컬 SSD(500GB)에 1차 저장**한다.
  타임스탬프 매니페스트와 함께 기록. 장기 보관은 필요 시 **연구실 데스크탑으로 오프로드**(Tailscale rsync,
  야간·유휴 시간). 가벼운 텔레메트리(온도·doneness·상태값)는 어디 저장하든 무방.
- **이유:** 카메라·센서가 Jetson에 물리적으로 붙어 있어 데이터가 거기서 생성됨 — **소스에서 기록**이 원칙.
  풀프레임을 실시간으로 네트워크에 흘려 다른 박스에 저장하는 건 낭비이고, 링크 끊기면 세션 데이터 유실.
  MQTT는 대용량 바이너리 채널이 아님. "찍고 나서 오프로드"가 안전.
- **주의:** 500GB 단일 SSD = 백업 없음 → SSD 고장 시 데이터 전손. 핫→콜드 오프로드(또는 로컬 백업통)로
  사본 확보 필요. 오프로드는 데스크탑이 **다른 WiFi**라 인터넷 업로드 속도에 묶임 → 영상 용량 산정 후 주기 결정.
- **대안:** T470s를 1차 저장소로(소스 아님 → 네트워크 낭비), 데스크탑 실시간 저장(링크 유실 위험).
- **날짜:** 2026-07-24

## D-007 · 기기 역할 확정 — 시스템 3대 vs 보조 장비
- **결정:** **배포 시스템 = Jetson + Pi + 로봇(3대)**. 그 외는 시스템 밖 보조 장비로 취급.
  - **Jetson** — 카메라·AI 추론·원시 데이터 저장(발행자)
  - **Pi 5** — Mosquitto 브로커 + 대시보드 서빙 (현장 상설, 헤드리스)
  - **로봇** — 외주. MQTT 구독 클라이언트(자동 재연결). 브로커 IP+토픽+`shared/schema.json`만 전달, 내부는 그쪽 관할
  - **엘리트북** — 일상 업무·개발용(주력)
  - **T470s(띵크패드)** — 시스템 밖. 헤드리스 Pi의 **뷰어 겸 제어 단말**(브라우저로 대시보드, SSH로 Pi 관리)
    + (옵션) Jetson 데이터 **로컬 백업통**. 필수 아님 — 없어도 시스템 완결.
  - **연구실 데스크탑** — (옵션) 원격 아카이브 타깃(D-006). 다른 WiFi, Tailscale로 연결.
- **이유:** "현장에 상설 설치"가 가능한 건 작고 싼 임베디드 박스(Pi)뿐 — 노트북은 현장 상설 부적합.
  반대로 개발·뷰어·백업은 노트북이 맡으면 됨. 각 장비를 억지로 파이프라인에 끼우지 않고 역할을 분리해 단순화.
- **대안:** 브로커/대시보드를 Jetson에 통합해 Pi 제거(→ 현장 상설 디스플레이 장비가 없어짐. PoC 단계엔 가능하나
  현장 배포엔 Pi 필요), T470s를 데이터 서버로(D-006에서 기각).
- **날짜:** 2026-07-24

## D-008 · Pi 헤드리스 운영 + 대시보드는 웹 브라우저로 접속
- **결정:** Pi는 **모니터 없이 헤드리스**로 운영한다. 대시보드는 Pi가 웹으로 서빙하고, 보는 쪽은
  같은 네트워크의 **브라우저**(T470s·엘리트북·태블릿 등)로 `http://<Pi-IP>:포트` 접속. Pi 관리·개발은 **SSH**.
- **이유:** 대시보드가 웹이라 표시 장치가 Pi에 물릴 필요 없음. 노트북은 화면이 **출력 전용**이라 Pi의 HDMI를
  받아 물리 모니터가 될 수 없음 — 하지만 브라우저+SSH면 Pi 데스크톱 자체가 불필요. 현장 설치도 단순해짐.
- **대안:** Pi에 모니터 직결(현장 상설 키오스크 필요 시 별도 저가 모니터 연결은 가능, `docs/PI5_SETUP.md` §5),
  노트북을 Pi 물리 모니터로(불가 — 입력 없음), VNC(Pi GUI가 꼭 필요할 때만).
- **날짜:** 2026-07-24

## D-009 · 네트워크 = 로컬 스위치(실시간) + Tailscale(원격), 스위치는 공유기 업링크
- **결정:** 두 평면으로 분리한다.
  - **로컬 실시간** — Jetson↔Pi MQTT·MJPEG·로봇은 **기가비트 스위치(유선)**. 인터넷 끊겨도 조리 시스템은 동작.
  - **원격** — 연구실 데스크탑 아카이브·원격접속은 **Tailscale**(다른 WiFi 간).
  - 스위치는 **공유기(라우터)에 업링크**해 인터넷을 물린다 → NTP 시간동기 + Tailscale 연결 확보.
- **이유:** 실시간 조리 트래픽은 로컬 유선이라야 지연·안정성 확보(WiFi로 MJPEG 흘리면 끊김). 스위치 단독은
  인터넷·DHCP·NTP·Tailscale 불가 → 타임스탬프 정합/원격백업이 막힘. 공유기 업링크로 해결.
- **대안:** 스위치 단독(인터넷·NTP 불가), 전부 WiFi(실시간 영상 불안정), 로컬 NTP 서버만 운영(원격백업 불가).
## D-010 · 도네스 모델 아키텍처 확정
- **결정:** RGB 2뷰(EfficientNet-B0 ×2, 뷰별 독립) + MLX90640 열배열(2D-CNN+1D TCN+수작업 공간피처)
  **late fusion** + MLX90614 온도 스칼라 **gated fusion** → **CORN ordinal 3단계** 헤드 +
  boil_intensity 보조 헤드. 배포는 전 branch **TensorRT fp16**, 추론 1 Hz. 상세: `docs/model-architecture.md`.
- **이유:** 벤치 실측(487 FPS)으로 속도가 비제약임이 확인돼 백본을 정확도 기준으로 선택 가능.
  RGB↔32×24 열배열은 픽셀 정합이 안 되므로 early stacking 배제(조사 3차). 완료↔과조리는 온도 포화
  구간이라 gated fusion으로 시각 신호에 자동 이양. INT8은 efficientnet에서만 이득이라 캘리브레이션
  비용 대비 채택 안 함.
- **대안:** MobileNetV3-Small 백본(전력 필요 시 폴백), early fusion+guided SR(LapGSR — ablation A2에서
  이길 때만), TSM/MS-TCN 시계열 승격(프레임 분류 불안정 시), INT8 양자화(전력 부족 시).
- **날짜:** 2026-07-24

## D-011 · Pi에 모니터 직결 (D-008 개정)
- **결정:** Raspberry Pi 5에 모니터를 직결한다. D-008의 "헤드리스 운영"을 개정 — Pi가 장비 관리 PC
  역할(인계 플랜 §2)을 맡으면서 현장 상설 관리 화면이 필요해짐. SSH·타 기기 브라우저 접속은 그대로 병행.
- **이유:** 관리 화면(촬영 시작/종료·상태 감시·전원 조작)은 장비 옆에서 즉시 조작할 일이 많고,
  Jetson이 꺼진 상태에서도 보여야 함 → Pi 직결 모니터가 가장 단순·확실한 경로.
- **대안:** 헤드리스 유지 + 노트북 브라우저(D-008 원안 — 장비 옆 즉시 조작 불편), 태블릿 거치(전원·거치 관리 추가).
- **날짜:** 2026-09-11

## D-012 · 열화상 = 보유 MLX90640 그대로 사용
- **결정:** 실험 장치의 열화상은 신규 구매 없이 **보유 MLX90640 2종(55°/110°)을 그대로 사용**한다.
  인계 플랜의 "열화상 모델·인터페이스 미확정"은 이것으로 확정. FOV 선택은 프레임 장착 거리 확정 후
  (`docs/model-architecture.md` §2.0 계산법).
- **이유:** 플랜이 제안한 선정 조건(온도 원시 데이터 확보)을 MLX90640이 충족(768개 ℃ 원시값, I²C).
  이미 보유·문서화돼 있어 추가 비용·SDK 리스크 없음.
- **대안:** 고해상 열화상 추가 구매(FLIR Lepton 160×120 등) — 32×24 해상도가 부족하다고 실측으로
  판명될 때만 재검토.
- **날짜:** 2026-09-11

## D-013 · Pi 관리 서버 = Python + FastAPI, 화면은 무빌드 정적 페이지
- **결정:** Pi의 장비 관리 서버는 **Python 3 + FastAPI**(`pi-server/`), 설정·이력은 **SQLite**,
  상시 실행은 **systemd**(`soup-pi-server`, 포트 8100). 관리 **화면은 빌드 단계 없는
  정적 HTML/CSS/JS**(`pi-server/app/static/`)로 서버가 직접 서빙한다. 기존 React 대시보드
  (포트 3000)는 **조리 데이터 뷰어로 그대로 유지** — 둘을 합치지 않는다.
- **이유:** ① 관리 서버는 GPIO(전원 제어)·프로세스 관리·네트워크 프로브를 하게 되는데 전부
  Python 생태계가 가장 단순. ② 관리 화면의 존재 이유가 "**Jetson·네트워크가 죽어도 뜨는 화면**"
  이므로 의존성이 적을수록 좋다 — 정적 페이지는 npm 빌드·Node 런타임 없이 Pi 부팅 직후 뜬다.
  ③ 조리 대시보드는 MQTT 텔레메트리(Jetson 살아 있어야 의미 있음)를 보는 화면이고 관리 화면은
  Jetson이 죽었을 때 가장 필요하다 — **가용성 요구가 정반대라 한 앱에 합치면 서로를 끌어내린다.**
- **대안:** React 대시보드에 관리 페이지 추가(코드 재사용은 좋으나 npm 빌드·Node 의존이
  관리 화면의 가용성 요구와 충돌, 대시보드 배포와 결합됨), Flask(비동기 감시 루프·
  스키마 검증에 추가 작업 필요), Node/Express(Pi에서 GPIO·시스템 제어 시 Python보다 불리).
- **날짜:** 2026-09-11

## D-014 · 제어 채널은 MQTT가 아닌 HTTP API (텔레메트리와 분리)
- **결정:** Pi 관리 서버 ↔ Jetson 수집 서비스의 **명령·상태 조회는 HTTP**(`docs/pi-jetson-api.md`).
  Jetson이 서버, Pi가 클라이언트. 기존 MQTT(`cooking/status`)는 **조리 텔레메트리 방송용으로 유지**.
- **이유:** 촬영 시작/중지는 "받아들여졌는지, 거절 사유가 뭔지"를 그 자리에서 받아야 하는
  요청-응답이다. MQTT로 하려면 요청/응답 토픽 쌍 + 상관관계 ID를 직접 만들어야 해서 더 복잡해진다.
  또 브로커(Pi)가 죽으면 제어까지 막히는데, 제어는 브로커와 무관해야 한다.
- **대안:** MQTT 요청/응답 토픽(구현 복잡·타임아웃 처리 직접 구현), gRPC(스키마 도구 부담),
  SSH 원격 명령(권한·감사 이력 관리가 어려움).
- **날짜:** 2026-09-11

## D-015 · 전원 제어는 "미지원"이 기본값 — 근거 없는 상태 표시 금지
- **결정:** 전원 제어 회로가 없으므로 관리 서버의 전원 기능은 **기본값 `unsupported`**로 두고,
  조작 요청은 **501**로 거절하며 화면에도 사유를 표시한다. 모의 조작은 `SOUP_POWER_MODE=mock`
  에서만 가능하고 응답·화면에 항상 `simulated: true`가 붙는다. 또한 상태 판정에서
  **"전원 꺼짐"은 전원 제어기가 OFF를 보고할 때만** 쓰고, 프로브 실패는 원인 미상
  **"연결 끊김"**으로만 표시한다(전원 OFF와 네트워크 단절을 구분할 수 없으므로).
- **이유:** 인계 플랜 §5의 "하드웨어가 없을 때 실제 전원을 제어하는 것처럼 보이게 만들지 않는다"를
  코드 기본값으로 못 박은 것. 관측(프로브 결과)과 추정(전원 상태)을 섞으면 나중에 실제 회로가
  붙었을 때 오작동을 잡아내기 어렵다.
- **대안:** 버튼을 그냥 두고 동작만 막기(오해 소지), 프로브 실패=전원 꺼짐으로 표시(네트워크
  단절 시 잘못된 판단 유도 — 플랜 §5가 금지한 "ping 실패 하나로 전원 차단" 경로의 시작).
- **날짜:** 2026-09-11

## D-016 · 기록 스키마 v2 — 열 추가 방식 확장 + 실험 기록은 보존 정책 제외
- **결정:** Pi 기록 스키마에 버전(`schema_version=2`)을 도입하고, 확장은 **`ALTER TABLE`
  열 추가만** 한다(기존 DB를 지우거나 재생성하지 않음). 보존 정책(자동 정리)의 대상은
  **세션과 무관한 운영 로그와 `host_metrics`뿐**이며, `sessions`와 **`session_id`가 붙은
  사건은 절대 자동 삭제하지 않는다**.
- **이유:** 실기기에 이미 운영 기록이 쌓여 있어 재생성은 손실이다. 또 "로그 정리"가
  연구 기록을 지우는 사고를 구조적으로 막아야 한다 — 정책이 아니라 쿼리 수준에서
  `session_id IS NULL` 조건으로 못 박았다. 내보내기 파일에도 `schema_version`을 실어
  나중에 해석 가능하게 한다.
- **대안:** 스키마 재생성 후 마이그레이션 스크립트(과함·위험), 보존 정책을 운영자 판단에
  맡기기(사고 시 복구 불가), 별도 아카이브 테이블로 이동(복잡도만 증가).
- **날짜:** 2026-09-12

## D-017 · 사건은 하나의 `events`로 통합하고 시각을 3종으로 구분
- **결정:** 조작·상태변화·오류·**수동 입력**(재료 투입·가열·교반·메모)을 별도 테이블로
  나누지 않고 `events` 한 곳에 모으되, `origin`(pi/jetson/manual)으로 구분한다. 시각은
  **`ts`(Pi 기록 시각) / `occurred_at`(실제 발생 시각) / `detail.sent_at`·`confirmed_at`
  (명령 보낸 시각·확인 시각)** 으로 나눠 저장하고, 한 조작의 사건들은 `request_id`로 묶는다.
  경과시간은 벽시계가 아닌 **monotonic**으로 재고, **기기 간 monotonic 비교는 금지**한다.
- **이유:** 조회·내보내기를 한 번에 하려면 한 테이블이 유리하다(실험 1건 = `session_id`
  필터 하나). 시각을 하나로 뭉개면 "언제 일어났는지"와 "언제 알았는지"가 영원히 구분
  불가능해진다 — 사후 입력과 장치 보고가 섞이는 이 장치에서는 치명적이다.
  `occurred_at`을 모르면 `ts`를 복사하지 않고 `null`로 둔다(모른다는 사실도 기록이다).
- **대안:** `marks` 별도 테이블(조회·내보내기 이중화), 시각 단일 필드(정보 손실),
  전역 시퀀스 없이 사건 나열(요청-응답 대응을 사람이 추측해야 함).
- **날짜:** 2026-09-12

## D-018 · "저장 완료"는 Jetson 요약 수신으로만 확정, 조작 출처는 신원을 지어내지 않음
- **결정:** ① 중지 요청 응답만으로 저장 완료로 기록하지 않는다. Jetson의
  `last_session_summary`(저장 결과 요약)를 받아야 `capture.save_confirmed`를 남기고
  세션에 박제한다. 요약이 없으면 화면·내보내기에 **`미확인`** 으로 남는다.
  ② 인증 기능이 없으므로 조작 사건에 **사용자 신원을 만들지 않는다** — `source`는
  `ui`/`api`, `detail`에 `client_host`와 `authenticated:false`만 남긴다.
- **이유:** ① "요청 성공"과 "실제로 저장됨"은 다른 사실이다. 둘을 같게 적으면 데이터가
  없는데 있다고 믿는 상태가 만들어진다(플랜 §4의 명시 요구). ② 로그인 없이 이름을
  적어 두면 나중에 그 기록이 증거로 쓰일 때 거짓이 된다. 관측 가능한 것만 적는다.
- **대안:** 중지 응답을 저장 완료로 간주(간단하지만 사실과 다름), 화면에서 사용자 이름
  입력받기(인증이 아니므로 위조 가능 — 신뢰할 수 없는 기록이 됨).
- **날짜:** 2026-09-12
